# A new HF game: open-source hosts

Research dated 2026-10-16. Private working report. Adam requested a fresh direction, preservation of both repair experiments, recovery of the original ideas, and research on open-source games or simulations that could become a different game with HF. No new game is selected or implemented by this report. Adam chooses the experience; a runnable integration and his play, not this ranking, accept a future game.

## What changes

Stop extending the workshop by default. Start from an existing host with visible places, usable controls and worthwhile activities. HF must alter consequential choices, not supply an explanatory panel beside a scripted game. Keep the original game's good movement, physics, tactical AI, economy and feedback. Replace only a small, explicit decision layer at first.

[The recovered original list](original-game-ideas-2026-10-16.md) distinguishes Adam's ideas from assistant proposals. The original five-row selection included delegation/training, procedural adaptation, population simulation, LLM NPCs and couple preferences. The Last Order, Repair House, Morning Bakery and Caravan Office were assistant theme proposals. Adam nearly chose Caravan Office before choosing the repair hook. Small-to-large progression and retained people remain useful directions, not a requirement to recreate the workshop elsewhere.

## The village projects

The remembered village is plausibly **Smallville**, from Stanford–Google Research's [Generative Agents](https://research.google/pubs/generative-agents-interactive-simulacra-of-human-behavior/). The paper describes 25 LLM agents with memories, reflection and plans. Its [original code](https://github.com/joonspk-research/generative_agents) includes a Django environment, a separate Python simulation process and replay. Code is Apache-2.0; separately credited art still needs asset-level review. The repository's last push was August 2024 when checked through GitHub's API. That does not itself establish whether a fork is maintained. Treat it as research prior art, not a production game or measured HF improvement.

**[Concordia](https://github.com/google-deepmind/concordia)** is Google DeepMind's Apache-2.0 Python library for generative social simulation. A game-master entity resolves natural-language actions. It requires an LLM interface and a text embedder for associative memory; its examples and editor are useful for social scenarios. It is not a ready-made village game. Borrowing its scenario construction and observation boundaries is more promising than nesting two authorities for person behavior. A structured HF-vs-LLM comparison is possible, but would need equal action/outcome rules; replacing prompts with HF is substantial redesign.

**[AI Town](https://github.com/a16z-infra/ai-town)** is a MIT TypeScript starter with a rendered town, pathfinding, conversations and agent scheduling. Its [architecture](https://github.com/a16z-infra/ai-town/blob/main/ARCHITECTURE.md) separates game inputs, simulation, rendering and agent operations. Actual source `convex/aiTown/agent.ts` exposes a tick-based agent decision layer; it also uses `Math.random()` and wall-clock state. HF can enter near this boundary without porting the framework to another language. That is an implementation hypothesis, not a working adapter. Convex backend, chat/embedding calls, data persistence and clock/RNG control still require work. The default loop is social conversation, so we would still need to design strategic play. Asset rights require separate checks. It can self-host Convex through Docker; no paid hosted account is inherently required. It is not a static-only app.

## Final recommendation after consultation and independent review

Keep two different goals explicit. For **playing inside an existing game**, Endless Sky is the provisional lead. For **watching and occasionally influencing a living place**, AI Town is the first candidate to inspect. Veloren stays a high-upside wildcard; its integration and action-heavy base are too uncertain to rank second as a practical recommendation. These are research priorities, not selected forks.

Astra ranked Endless Sky, CDDA and OpenTTD by inherited game systems. Root instead emphasizes visible person interaction, which raises AI Town. Independent review correctly rejected treating these as one unexplained top-three list. CDDA and OpenTTD remain useful reserves with explicit mismatches, not equal recommendations. Ambient simulation is a valid outcome; Adam need not enjoy manual piloting to value an inhabited space simulation. If Endless Sky's active game is not the goal, test spectator/occasional-intervention appeal directly.

One adjacent comparison should happen before committing to an Endless Sky engine fork: **[Naev](https://naev.org/)** supplies space exploration, trade and combat, an integrated plugin manager, and Lua missions/scripts over a Rust/C engine. Its [GitHub mirror](https://github.com/naev/naev) points to [Codeberg upstream](https://codeberg.org/naev/naev). Existing scripting might reduce invasive changes, but npm compatibility and persistent-person integration remain unproven. The public API page could not be read in this pass, so this is a screen, not a source-level endorsement. No need to expand the whole shortlist again.

Recommendation for the next comparison: inspect unchanged Endless Sky alongside Naev for one named captain, and inspect AI Town for a person performing a non-chat activity. Then choose the desired experience before selecting a fork or implementing HF. Do not begin another broad game rewrite from this report.

## What would make each lead worth playing

**Endless Sky: a small convoy, not a galaxy of full HF agents.** Keep piloting, combat, trade and upgrades. Three named captains can choose whether to honour an escort commitment, continue after damage, take refuge or help someone they distrust. The player plans a route and negotiates shared risk. Actual outcomes change future availability and willingness. A journey can be watched at accelerated speed or played directly; a screensaver is an observation mode, not the whole game. Do not turn flight controls into a manager panel.

**AI Town: a physically visible neighbourhood with competing plans.** Start with an existing map and walking controls. A few people share a scarce vehicle or meeting space. The player also has a concrete objective in that place. People receive invitations, travel, work, rest and keep or revise commitments through actual events. Repeated clicking cannot advance time for free. This is a proposed game loop that the host does not already supply. Reject it if play becomes reading summaries of meetings and manipulating schedules again.

**Veloren: one companion on a journey.** Keep exploration, travel and combat in the engine. Give one traveller a persistent HF person state. Choosing a destination or helping an injured stranger changes who accompanies the player and what can be done next. Prove continuity through loading/unloading before adding a settlement. Avoid claiming the whole living economy or relationships are already implemented in rtsim.

## HF boundary and a discriminating experiment

HF 2.2.1 is TypeScript and already owns bounded choices, person snapshots, relationships/needs and demonstrated conditional methods. It is not a drop-in unrestricted planner. The host must construct meaningful offers and percepts, enforce physical feasibility and resolve outcomes. A legal action menu is necessary; secretly preselecting the desired action then asking HF to narrate it is not integration.

For native hosts, first try a coarse local Node sidecar with structured observations and decisions at meaningful boundaries, not every frame. Keep movement/combat/pathfinding in the host. A sidecar is only a candidate design: process lifecycle, packaging, timeout policy, canonical snapshot synchronization, save/resume, and multiplayer implications remain untested. No port or vendoring of HF is implied. A different runtime arrangement must preserve published-package provenance.

A first technical spike should answer one question: can one named person choose differently because of acquired experience while every relevant host fact stays the same? Run paired cases from one world seed: intact HF state, restored pre-experience state, and host's original policy. Match exogenous events independently of actor draw order. Show the behavior in the host's normal view. Then give a source-unread player a short situation. Technical causality and experience value are separate tests. In active play, they must notice an interesting consequence and want another attempt. In an ambient simulation, the test is whether they want to keep watching and whether a small intervention visibly changes subsequent events. A result can fail either technical causality or player interest; do not compensate by building more systems.
